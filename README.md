# 🛡️ StreamShield

### Intelligent Video Piracy & Account-Sharing Detection Platform

StreamShield is a full-stack streaming security platform designed to address **unauthorized account sharing, suspicious streaming behavior, and video piracy**.

Instead of treating authentication as the end of the security process, StreamShield continuously analyzes streaming activity using **behavioral telemetry, forensic watermarking, graph-based relationship analysis, rule-based anomaly detection, and machine learning**.

The platform provides two distinct experiences:

* 👤 **Regular User** — registers, browses movies/content, and watches videos through the streaming platform.
* 🛡️ **Administrator** — monitors streaming activity, analyzes user/device/IP relationships, and investigates suspicious behavior through an administrative dashboard.

# 🎯 Problem Statement

Modern streaming platforms face several related security challenges:

* Users sharing their credentials with others
* One account being used across many devices
* Suspicious access from different IP addresses or locations
* Unusual streaming patterns
* Unauthorized screen recording and redistribution
* Difficulty connecting suspicious sessions to a common source

Traditional authentication can answer:

> **"Is this user allowed to access the platform?"**

StreamShield attempts to answer a more useful security question:

> **"Does this user's streaming behavior appear legitimate, and can suspicious activity be investigated or traced?"**

To address this, StreamShield combines multiple layers of security and analysis rather than relying on a single detection technique.

# 🎥 2. Dynamic Forensic Watermarking

One of StreamShield's key security features is **session-specific forensic watermarking**.

Instead of using only a static watermark, identifying information can be dynamically associated with the current viewing session.

The objective is to make unauthorized screen recordings potentially traceable back to the originating session.

### Conceptual flow

```text
User Login
    ↓
Authenticated Session
    ↓
Session Identifier
    ↓
Video Playback
    ↓
Dynamic Watermark
    ↓
Screen Recording
    ↓
Potential Source Identification
```

### Why forensic watermarking?

If a protected video is recorded and redistributed, the captured content may contain session-specific information that can assist with investigating its origin.

> The watermark is intended as a **forensic identification layer**, not a guarantee that screen recording or piracy can be completely prevented.

# 🕸️ 4. Graph-Based Threat Detection

A major component of StreamShield is its graph-based representation of streaming activity.

Users, devices, IP addresses, and sessions can be treated as connected entities.

For example:

```text
             User A
            /      \
           /        \
      Device 1    Device 2
          |           |
        IP A        IP B
           \         /
            \       /
             Session
```

This representation makes it possible to investigate relationships that would be difficult to identify using isolated database records.

---

## 🔎 Breadth-First Search

**BFS (Breadth-First Search)** is used to traverse connected entities.

For example:

```text
User
 ↓
Device
 ↓
IP
 ↓
Session
 ↓
Other Connected Entity
```

BFS can help explore the neighborhood around a suspicious entity and identify related activity.

---

## 🔗 Union-Find

**Union-Find / Disjoint Set Union** can be used to identify connected components efficiently.

For example:

```text
User A ─ Device 1 ─ IP X
User B ─ Device 2 ─ IP X

User C ─ Device 3 ─ IP Y
```

The first two users share a relationship through `IP X`.

Union-Find can group such connected entities into components that can subsequently be investigated.

## ⚡ Stage 1 — Rule-Based Detection

The first layer provides fast anomaly detection.

Potential indicators include:

* Unusual session activity
* Excessive concurrent usage
* Unexpected device changes
* Abnormal geographic patterns
* Repeated access from different environments

The main advantages of rule-based detection are:

* Low latency
* Easy interpretation
* Deterministic behavior
* Simple operational debugging

---

# 🤖 Stage 2 — Machine Learning

For more complex behavioral patterns, StreamShield incorporates machine-learning models.

The project uses models such as:

* **Random Forest**
* **XGBoost**

These models can analyze behavioral telemetry/features to identify patterns that may not be captured by simple rules.

### ML pipeline

```text
Raw Telemetry
      ↓
Feature Extraction
      ↓
Feature Engineering
      ↓
Training Data
      ↓
Random Forest / XGBoost
      ↓
Behavioral Prediction
      ↓
Risk Assessment
```

The ML layer complements the deterministic rules rather than replacing them.

---

# ⚖️ Why Hybrid Detection?

A purely rule-based system is fast and interpretable but can struggle with complex patterns.

A purely ML-based system can identify more complex relationships but introduces challenges such as:

* Training-data dependency
* False positives
* Model maintenance
* Reduced interpretability
* Prediction overhead

StreamShield therefore uses both approaches.

```text
                  ┌───────────────┐
                  │ Rule Engine   │
                  └───────┬───────┘
                          │
Telemetry ────────────────┼──────────────► Risk Assessment
                          │
                  ┌───────▼───────┐
                  │ ML Detection  │
                  └───────────────┘
```

# ⚠️ Limitations

StreamShield is a security-focused engineering project and is **not intended to guarantee complete prevention of piracy**.

### Forensic watermarking

Client-side or visually rendered watermarks can potentially be:

* Cropped
* Obscured
* Manipulated
* Removed using sufficiently sophisticated techniques

### IP-based analysis

An IP address does not necessarily identify a unique individual.

For example, multiple legitimate users may share:

* The same household network
* University Wi-Fi
* Corporate networks
* Public networks
* VPN infrastructure

Therefore, IP relationships should be treated as **signals rather than definitive evidence**.

### Machine Learning

ML performance depends on:

* Training-data quality
* Feature quality
* Data distribution
* Model selection
* False-positive/false-negative tradeoffs

Therefore, model predictions should be treated as **risk indicators requiring contextual interpretation**.
